# CipherVault Threat Model

## Objective

Protect message confidentiality and integrity against an attacker who knows the CipherVault format and possesses the ciphertext, but does not possess the password.

## Covered attacker

- Obtains stored or intercepted ciphertexts.
- Knows the source code and public parameters.
- Can alter ciphertext bytes.
- Can attempt passwords offline.
- Can provide malformed inputs to the parser.

## Not-covered attacker

- Malware with access to the process, memory or keyboard.
- Keylogger.
- Screen capture.
- Operating-system compromise.
- Control of the GitHub/release environment.
- Host compromise during execution.

## Provided properties

- Plaintext confidentiality under the security of the password and AES-256-GCM.
- Integrity and authentication of the ciphertext and AAD.
- New messages use random salt and nonce values.
- The SC4 format binds the version, algorithm and PBKDF2 iteration count through AAD; fixed field sizes are enforced structurally.

## Properties not provided

### Identity authentication

AES-GCM authenticates the message for whoever possesses the derived key, but it does not prove which person produced it. Sharing the same password means sharing the ability to produce valid messages.

### Anti-replay

CipherVault does not maintain state to prevent an authentic ciphertext from being replayed. If the context requires anti-replay, the protocol needs state or an external sequencing mechanism.

### Weak-password resistance

Key derivation uses PBKDF2-HMAC-SHA256 with 600,000 iterations. This increases the cost of attempts, but does not turn a weak human password into a strong password. OWASP recommends 600,000 iterations for PBKDF2-HMAC-SHA256 when PBKDF2 is required, and prefers Argon2id when available.

### Local exposure

The application uses PowerShell strings for plaintext and password in some stages. The managed runtime does not provide deterministic erasure of every copy of those strings.

### Clipboard

Ciphertext can be copied automatically to the clipboard. Ciphertext is not secret by itself, but it may be synchronised or observed by other applications depending on system configuration.

## GCM considerations

The 96-bit nonce is generated by a CSPRNG. NIST treats IV/nonce uniqueness for a given key as critical and recommends 96 bits for simplicity and efficiency.

## Architecture decision

CipherVault deliberately remains free of external cryptographic dependencies. This reduces the supply-chain surface, but means PBKDF2 remains the available KDF for deriving a key from a password.
